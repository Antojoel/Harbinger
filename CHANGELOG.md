# Changelog

All notable changes to this project are documented in this file.

Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed
- `docker-compose.yml`'s `stt`/`tts` services (Vignesh's V5 local voice pipeline, merged to `main`) had `gpus: all` unconditional and `tts` defaulted to a CUDA torch wheel — a plain `docker-compose up --build` on a non-GPU machine hung downloading a multi-GB CUDA build and would have failed outright at container start (no GPU passthrough on Docker Desktop for Mac). Confirmed live while testing. Made both services opt-in via a compose profile (`docker compose --profile voice-local up`) and CPU-default otherwise. Neither the dashboard's VoiceWidget (browser Web Speech API) nor the locked contract's default `text_only` voice provider need these services at all, so the default `docker-compose up` path never depends on a GPU. Verified `docker compose config --services` excludes them by default and includes them with the profile flag.

### Changed
- **A9: Google Sign-In + first-time onboarding walkthrough.** New `core/user_store.py` (in-memory users) and `integrations/google_auth.py` (verifies Google ID tokens, issues our own session JWTs). New endpoints: `/api/auth/google`, `/api/auth/guest`, `/api/auth/me`, `/api/auth/onboarding-seen`; `/api/config` now also reports `google_login_configured`. Frontend: `AuthContext.jsx`, `Login.jsx` (Google button + guest fallback), `OnboardingTour.jsx` (5-step modal on first login), a logout control in the header. Deliberately scoped auth to the dashboard UI only — none of the existing business endpoints were put behind a login check, since that would break the MCP server's existing unauthenticated calls and contradict the product's "connect via REST or MCP" positioning. Degrades gracefully like Razorpay: no `GOOGLE_CLIENT_ID` set → "Continue as Guest" instead of a hard wall, verified both paths. Apple Sign-In was scoped out entirely — it needs a paid, pre-verified Apple Developer account and domain verification, not achievable in the time left. Verified end-to-end: guest login → session resume on reload → onboarding completion → persisted across reloads. New env vars in `.env.example`: `GOOGLE_CLIENT_ID`, `VITE_GOOGLE_CLIENT_ID`, `SESSION_SECRET`.
- **A8 done for real: live Razorpay test-mode integration.** `services/engine/app/integrations/razorpay_client.py` creates real orders and verifies real HMAC signatures via the official SDK, reading `RAZORPAY_KEY`/`RAZORPAY_SECRET` from the environment (never hardcoded). Wired into both the locked `/api/create-payment-order`+`/api/verify-payment` and the UI-adapter `/api/payments/*` endpoints. `/api/pricing`'s `razorpay_ready` now reflects real configuration state. Verified live against Razorpay's actual test-mode API (real order IDs came back) and confirmed a fake signature is correctly rejected, not rubber-stamped. Still degrades to `{"awaiting_keys": true}` for anyone without credentials set. Added `.env.example` documenting the required vars; `docker-compose.yml`'s `engine` service now passes `RAZORPAY_KEY`/`RAZORPAY_SECRET` through via `${VAR}` substitution from the root `.env`.
- **Frontend ported and migrated off CRA to Vite.** Found a complete, independently-built frontend (and a bespoke Mongo+FastAPI backend, discarded) sitting untracked at `apps/ClearanceGuard-main`, built with an AI app-builder (Emergent) against its own API shape. Extracted just the frontend into `apps/web`, replacing the never-implemented Vite skeleton (archived to `archive/apps-web-vite-skeleton`). It was built for CRA/craco; migrating to Vite cut the install from 1522 packages to 287 and avoided an unresolvable `ajv`/webpack toolchain conflict in the CRA build. Removed Emergent's own telemetry (PostHog) and branding script tags from `index.html`; pruned the shadcn/ui kit and dependency list down to only what's actually imported (17 of ~48 scaffolded UI components).
- New backend surface to support the dashboard: `services/engine/app/core/shipment_store.py` (in-memory shipment catalog, 6 shipments seeded to trigger real contradictions against Vignesh's actual Neo4j data) and `services/engine/app/api/ui_adapter.py` (translates the locked contract into the dashboard's richer shape). New endpoints in `routes.py`: `/api/stats`, `/api/shipments`, `/api/shipments/{id}`, `/api/approve-fix`, `/api/outcome`, `/api/pricing`, `/api/payments/order`, `/api/payments/verify`, `/api/voice`, plus stubs for the out-of-scope email/integrations pages (`/api/config`, `/api/email/*`, `/api/integrations`) so those routes don't crash. `/api/simulate` and `/api/record-outcome` extended additively (new fields merged in) — the MCP server and any other consumer of the original contract are unaffected.
- `services/stt/` now defaults to **faster-whisper** (Whisper on CTranslate2), selectable via `STT_ENGINE` (`faster_whisper` | `sherpa`). faster-whisper is far more accurate on free-form speech than the streaming Zipformer transducer, has a built-in VAD, and runs on CUDA automatically when a GPU is visible (`STT_DEVICE=auto` → `cuda`/`float16`, else `cpu`/`int8`, with a CPU fallback if the CUDA load fails). Default weights (`small.en`) are baked into the image. New env: `STT_ENGINE`, `STT_WHISPER_MODEL`, `STT_DEVICE`, `STT_COMPUTE_TYPE`, `STT_LANGUAGE`, `STT_BEAM_SIZE`, `STT_VAD_FILTER`. The sherpa / Kroko path is unchanged and still available.
- `docker-compose.yml` — `stt` and `tts` now request the GPU (`gpus: all`); the `tts` image builds against a CUDA torch wheel by default (`TORCH_INDEX_URL`, override to `.../whl/cpu` for a CPU-only box). Removed the `stt-models` volume (weights are in the image).
- Reassigned the voice pipeline (`A7`, now `V5`) from Anto to Vignesh, and from Vertex AI to a local model. The AI Grants India key (`.env`) was tested directly against `/v1/models` and only exposes `gpt-5-nano` (text-only, no audio models); Vertex AI is also currently unusable. Vignesh has a local-model workaround (`--jinja`).
- `.gitignore` now excludes `.env`/`.env.*` — it was untracked but not ignored, so a broad `git add` could have leaked the API key. Verified it was never actually committed before fixing.

### Added

  - `services/engine/app/voice/` — `text_only` (default; no speech infra, `audio_base64` treated as UTF-8 text), `openai` (`/audio/transcriptions` + `/audio/speech`), `gemini` (`generateContent` STT + TTS, PCM wrapped to WAV), and `local` (calls the bundled `stt` / `tts` services). Provider construction falls back to `text_only` on missing credentials so the endpoint never hard-fails.
  - The spoken answer is computed locally and deterministically from the graph (shipment status + matched patterns via `graph_client.execute_read`) — no LLM in that path. A speech-provider failure degrades to an empty transcript / empty audio but the text answer is always returned.
  - `services/engine/app/api/routes.py` — `/api/voice-query` now calls the real pipeline instead of returning a hardcoded stub.
  - 36 unit tests (`text_only`/`openai`/`gemini`/`local` via `httpx.MockTransport`, the graph-driven answer, and the orchestrator's degradation paths).

Ships with a fully public default model; set `STT_HF_REPO=Banafo/test-onnx` + `STT_HF_TOKEN` for the real Kroko community models, or mount a model dir with `STT_MODEL_DIR`.

### Fixed
- **Blank white screen crash on any browser where Google's script actually loads (Safari included, not just the Brave-blocked case).** `Login.jsx` rendered a React-controlled loading spinner *inside* the same DOM node that `google.accounts.id.renderButton()` also writes into directly, outside React's control. The instant the button rendered, React tried to remove its spinner from a node Google had already rewritten — `Uncaught NotFoundError: Failed to execute 'removeChild'`, crashing the whole tree with no error boundary. Restructured so the ref'd node Google owns never receives React children at all; the spinner is now a sibling overlay. Also added a one-shot guard so `initialize()`/`renderButton()` can only ever fire once, since StrictMode's double-invoke would otherwise call `renderButton` twice into the same node.
- `docker-compose.yml`'s `engine` service depended on `neo4j` with `condition: service_started` — that only waits for the container to start, not for its healthcheck to pass. On a real `docker-compose up`, the engine could open its one-shot Neo4j connection before Neo4j's bolt port was actually ready, and since that connection attempt never retries, it stayed permanently in degraded mode (empty results, no crash, no obvious error) until manually restarted. Changed to `condition: service_healthy`. Verified via a full clean `docker-compose down && up`: compose now visibly waits for "Neo4j Healthy" before starting the engine, which connects cleanly on the first try every time.
- `Login.jsx`'s Google Identity Services polling loop had no retry cap — if `window.google` never loads (e.g. blocked outright by Brave Shields or an ad blocker, which is common), it polled every 150ms forever, pegging the tab. Reported as "localhost:3000 not working." Capped at 20 attempts (~3s), then shows a clear "Google sign-in didn't load, use guest login" message instead of spinning indefinitely. Also hardened `AuthContext.jsx`'s two mount effects with ref guards so they can never fire more than once regardless of React StrictMode's double-invoke behavior.
- `docker-compose.yml` had no `restart` policy on any service — recreating one container (e.g. `engine` for an env var change) silently left dependent containers like `mcp-server` exited with no indication anything was wrong. Added `restart: unless-stopped` across all four services.
- Neo4j had no persistent volume — any container recreation (including a plain `docker-compose up` after a config change) silently wiped the entire seeded graph, with nothing telling you it happened. Added a named volume (`neo4j_data`). Verified data now genuinely survives a `--force-recreate` of the Neo4j container. Also surfaced a smaller related issue while testing this: the engine's Neo4j driver doesn't automatically reconnect if Neo4j restarts while the engine stays up — queries silently return empty results (degraded-mode behavior, not a crash) until the engine itself is restarted. Not fixed here (Vignesh's file); noting it as a known limitation.
- `main.py` imported a `graph.neo4j_client` module that didn't exist, which would have crashed the app on startup.
- `record_pattern()` (Vignesh) overwrote an existing pattern's stored `detail` with a generic fallback string on every reinforcement; the caller-supplied detail is now only written when provided, with a separate fallback used on node creation.
- `record-outcome` and `graph` endpoint responses didn't match the documented API contract (wrong field names, `source/target/label` instead of `from/to/type` on graph edges); `patterns` returned a bare array instead of `{"patterns": [...]}`. All aligned to the contract and verified against a running instance.
- Reconciled a git divergence: Vignesh's real graph layer (V1-V4) was built against the placeholder `neo4j_client.py` interface from before A4 existed, and diverged from what `engine.py` actually called (different method names/signatures, `Pattern`/`GraphSnapshot` dataclasses vs. the dicts A4 expected). Merged `origin/main` and rewrote `engine.py`'s `simulate()`/`record_outcome()`/`query_patterns()`/`graph_snapshot()` to call the real interface correctly, and removed A4's local contradiction-detection logic since `graph_client.find_matching_patterns()` already applies `graph.rules` internally — that was becoming a second, divergent implementation of the same business rules.
- `SimulateRequest` in `routes.py` never declared a `country` field; Pydantic was silently dropping it before it reached the engine, so certificate-requirement lookups could never resolve a destination country. Added the field.
- Verified the full pipeline against a real, seeded Neo4j instance (not just degraded/stub mode): `/simulate` correctly matches real stored patterns, and `/record-outcome` genuinely reinforces them (`PAT-001` frequency 14→15, confidence 0.82→0.83 after one recorded outcome).
- Merged Vignesh's real A6 MCP server branch; only real conflict was in `TASKS.md` (both sides edited the same lines), resolved by keeping both completion notes. Verified through the actual MCP protocol (a real client, not just a syntax check) end-to-end: `check_shipment_risk` and `record_outcome_tool` both work through the full server → engine → Neo4j chain.
- My own first attempt at the ported frontend's seed data had `shp-0045`'s HS-code-mismatch case built wrong — `detect_hs_code_mismatch()` compares the invoice's HS code against the shipment's *declared* HS code, not against the bill of lading, which is what I'd used. It silently scored 0% risk instead of the intended mismatch. Fixed the seed data (`shipment_store.py`) and confirmed it now scores correctly.
- The CRA build failed on `Cannot find module 'ajv/dist/compile/codegen'` — a version mismatch between the resolved `ajv@6` and `ajv-keywords@5` (needs `ajv@8`), and separately on `EALLOWREMOTE` fetching `@emergentbase/visual-edits` from Emergent's private asset server. Both moot after migrating to Vite, which doesn't hit either.
